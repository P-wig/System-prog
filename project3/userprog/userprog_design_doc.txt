>> B3: Describe your code for reading and writing user data from the
>> kernel.

The kernel can directly dereference pointers but before doing that we first validate with check_user_range to make sure the address is in user space and that it is actually mapped. Within check_user_range,  pagedir_get_page() is called to validate that each page is mapped. 

arg_word validates syscall arguments from the user before dereference
check_user_string validates at page boundaries for NULL terminated strings

On any failure we call sys_exit terminating the process

>> B5: Briefly describe your implementation of the "wait" system call
>> and how it interacts with process termination.
>>
When a process is executed process_status creates a process status which has exit code, semaphores, and other meta data which is populated by the child before signaling the dead semaphore. process_wait scans children for matching child on that semaphore until exit, and returns exit.

>> B6: Any access to user program memory at a user-specified address
>> can fail due to a bad pointer value.  Such accesses must cause the
>> process to be terminated.  System calls are fraught with such
>> accesses, e.g. a "write" system call requires reading the system
>> call number from the user stack, then each of the call's three
>> arguments, then an arbitrary amount of user memory, and any of
>> these can fail at any point.  This poses a design and
>> error-handling problem: how do you best avoid obscuring the primary
>> function of code in a morass of error-handling?  Furthermore, when
>> an error is detected, how do you ensure that all temporarily
>> allocated resources (locks, buffers, etc.) are freed?  In a few
>> paragraphs, describe the strategy or strategies you adopted for
>> managing these issues.  Give an example.

* Before any work is started we validate and if we encounter any errors we terminate immediately.

* Every user supplied pointer is validated using check_user_range before the kernel dereferences it. This makes sure that we are in user space and that it is mapped in the page directory (pagedir_get_page). arg_word does the same validation to syscall arguments on the user stack. We also have guard clauses such as check_user_range whcih just throws out possible overflows and size == 0, and check_user_string, which validates strings at page boundaries rather than per byte. 

* If we encounter any failure we call sys_exit(-1) and terminate the process. For syscalls that require resources we only allocate after validation.


---- SYNCHRONIZATION ----

>> B7: The "exec" system call returns -1 if loading the new executable
>> fails, so it cannot return before the new executable has completed
>> loading.  How does your code ensure this?  How is the load
>> success/failure status passed back to the thread that calls "exec"?
* success and failure is tracked in the struct process_status on the member bool load_success. This struct is shared, and we block until that is complete. The child thread sets ps->load_success and then calls sema_up and process_execute calls sema_down which blocks. After the parent wakes up it will check ps->load_success and if it is false it will replace the childs TID with TID_ERROR and returns that. The struct also contains a reference count keeps the process alive to prevent use after free errors or being garbage collected.


>> B8: Consider parent process P with child process C.  How do you
>> ensure proper synchronization and avoid race conditions when P
>> calls wait(C) before C exits?  After C exits?  How do you ensure
>> that all resources are freed in each case?  How about when P
>> terminates without waiting, before C exits?  After C exits?  Are
>> there any special cases?
>>
* When the parent calls wait(c) before C exits the process_wait() calls sema_down(&ps->dead) which blocks. The child once complete calls sema_up(&ps->dead) when it exits on process exit. 

* After C exits, the parents sema_down is unblocked, which then the parent will evaluate the exit code, afterwards the process_status() is cleaned up in release_child_status().

* When parent terminates without waiting the process_exit() iterates through the children list and calls release_child_status on each. The process_status still has a reference count so it will not be cleaned up.

* After C exits (if the parent already exit) that would be an orphan process, the parents process_exit() would have already reduced the ref_cnt when the child process calls process exit() it would still call sema_up(), though nothing would track it and then call release_child_status reducing the ref_cnt to 0 and the resources would be freed.

* special cases, calling wait twice for the same child, the second time returns a -1 because list_remove in the first process_wait() removed it from the childrens list.

* bad TIDs or TID collision with siblings, 

* Parent exits before calling wait(), this would cause the children to become orphans, holding onto resources such as process_status until the process exits.

>> B9: Why did you choose to implement access to user memory from the
>> kernel in the way that you did?
* simplicity, every function that uses a user pointer first checks if its in userspace then validates the mapping with a page dir lookup, then we dereference it directly. Its kind of like lazy loading or just in time, so we dont need a buffer or any malloc calls. If any parts fails, we terminate the process.

>> B10: What advantages or disadvantages can you see to your design
>> for file descriptors?
>>
* Simplicity, again is an advantage, every process gets an allocation, and a clean up. Disadvantage is the basic for loop with O(N) look up speed for file descriptors. We also do not reuse file descriptors so at some point we are going to run out.

>> B11: The default tid_t to pid_t mapping is the identity mapping.
>> If you changed it, what advantages are there to your approach?
* We could have process groups like in yash, that way we could send signals to entire groups of processes, which would allow us to have job control, or also allow children to look up their parent processes.
